# Shared implementation contract

Version 2 (app 1.1.0). Source of truth: `src/lib/types.ts` and the applied SQL migrations. Decimal values travel as strings. Public RPCs:

Financial policy: product sale prices use at most 2 decimal places; raw ingredient reference prices and purchase unit costs support up to 6. Purchase document totals round once to cents after the exact sum of every line (not per line). Frontend Decimal precision is 48. Operational dates use Mendoza, Argentina. Pending transport-uncertain commands retain their original UUID across application restarts; they are not an offline-write queue.

- `app_snapshot()` -> `schema_version: 2`, exact `Snapshot` JSON shape, arrays present even when empty; money/stock numeric values encoded as strings.
- `app_command(p_command_id uuid, p_operation text, p_payload jsonb, p_expected_version integer default null)` -> `{id, affected_order_ids}`. No Auth. Global advisory transaction lock before any domain reads. Idempotency checks occur before version checks. Errors use `VALIDATION_ERROR`, `INSUFFICIENT_STOCK`, `INSUFFICIENT_RESERVED_STOCK`, `INVALID_TRANSITION`, `VERSION_CONFLICT`, `IDEMPOTENCY_CONFLICT` in message text.

Payloads (id absent=create; expected_version is separate RPC arg):

- save_client: `{id?,name,phone?,email?,address?,notes?,pets?:[{name,weight_kg:string|null,diet}]}`. Edits use client version; omitted added fields preserve existing values.
- save_item: `{id?,kind,name,unit,price,minimum,active,category?,code?,presentation?,weight_kg?}`. Products unit=unidad. Ingredient catalog unit cannot change after movements/recipe use. All balances are in catalog unit; purchase/recipe unit conversion supports g/kg and ml/l only.
- save_recipe: `{product_id,yield_quantity,lines:[{ingredient_id,quantity,unit}]}` creates a new immutable revision; expected_version is latest recipe revision (0 for none).
- save_order: `{id?,client_id,pickup_date,location_id,payment_method,notes,lines:[{product_id,quantity}],pickup_time?,uber?,packages?,prepared_packages?,delivery_notes?,payment_status?:'pagado'|'no_pagado',transfer_name?:string|null}`. Unique product lines. Server snapshots catalog price for new lines, retains existing prices for retained lines. No arbitrary price payload accepted.
- deliver_order: `{id,payment_status?:'pagado'|'no_pagado',method?:'efectivo'|'transferencia',transfer_name?:string|null}`; pending only. Explicit paid atomically collects the remaining balance; unpaid never alters previous receipts. Legacy `{id}` remains delivery-only.
- cancel_order: `{id}`; only pending orders.
- reschedule_order: `{id,pickup_date}` with order version; pending only, changes only the date and recalculates reservations. Closed location/date targets reject with `PICKUP_CLOSED`.
- set_pickup_closure: `{location_id,pickup_date,closed:boolean,reason?:string}`; closing requires zero pending orders at that exact location/date, regardless of visible filters. Reopening deletes the closure; optional expectedVersion guards existing closure edits.
- save_purchase: `{id?,supplier,expected_date,notes,lines:[{ingredient_id,quantity,unit,unit_price}]}`; only planned may edit. receive_purchase: `{id,manufactured_on?,batch_code?}`; cancel_purchase: `{id}`. Known manufacture dates are recorded; omitted dates explicitly estimated.
- plan_production: `{product_id,recipe_id,planned_date,target_quantity,notes}`.
- start_production: `{id}`. finish_production: `{id,actual_quantity,actual_ingredients?:[{ingredient_id,quantity,unit,waste_quantity}],manufactured_on?,batch_code?}`; actual_quantity positive integer. Useful consumption plus additional waste reconciles estimated start consumption through delta movements. Each production stores an immutable recipe_snapshot. cancel_production: `{id,reason}`; cannot cancel completed. Ingredient quantities proportional to target/yield and converted to catalog units; consume on start only.
- transfer_stock: `{item_id,from_location_id,to_location_id,quantity,reason}` finished goods only, positive integer, unreserved stock only.
- adjust_stock: `{item_id,location_id,quantity,reason,manufactured_on?,batch_code?}` signed DELTA, not replacement; ingredients central only. Zero delta forbidden. Rebalance reservations after loss.

## Version 2 operations and invariants

- `save_location {id?,name,color,active,is_pickup}`; edits require expectedVersion. Kitchen remains active and non-pickup; locations with pending orders cannot be deactivated. Retaining an inactive original pickup while editing its order is supported.
- `record_payment {order_id,amount,method,occurred_on?,notes?,transfer_name?:string|null}`; positive cents, no overpayment, order version increment. Editing cannot shrink a sale below net payments; cancellation requires correcting receipts first.
- `record_refund {order_id,amount,method,occurred_on?,notes?}`; closed returned/canceled orders only; caps deferred reimbursement to residual net receipts and increments version without repeating any stock movement.
- `record_expense {amount,method,category,occurred_on,notes?,purchase_id?}`; positive input, negative cash ledger. Supplier payments and expenses are separate from purchase receipt.
- `reconcile_movement {id,reconciled}` with expectedVersion; reconciliation changes no amount.
- `reverse_financial_movement {id,reason}`; immutable opposite-signed entry. Does not permit negative net receipts after refunds; linked order version advances.
- `return_order {id,reason,restock,refund_amount?,method?}` with expectedVersion; full delivered order only, never repeats. Physical restocking is optional and retains original batch identity. The original delivered status/history stays, with returned_at/return_reason/restocked.
- `reverse_movement {id,reason}`; adjustments and complete transfers only, once. Requires original batch inventory still free and does not displace current usable reservations. Original rows are never overwritten.
- `app_export()` -> `{format:'pedidos-stock',schema_version:2,exported_at,data:Snapshot,raw_tables,idempotency_commands}`. All decimal money/quantity fields, including raw tables, are strings. UI adds embedded SHA-256; CLI creates a sidecar checksum. See RECOVERY.md.

Snapshot adds batches, batch_stock, movement_batches, financial_movements, audit_events. All physical changes still derive exclusively from immutable movements. Batch allocations cover raw ingredients and finished products across receipts, adjustments, transfers, production, delivery, returns and reversals. Manufacturing + four calendar months determines expiration, with month-end clipping. Unknown historical dates are marked estimated and historical consumption is preserved during migration replay; this does not exempt new commands from expiration checks.

Public order_allocations computes canonical reservations using unexpired batch stock and pickup date/creation priority on every read, including date changes overnight. Physical on_hand retains expired units for traceability/disposal; expired units are not usable or deliverable. Commands serialize the corresponding persisted allocations transactionally. Snapshot includes derived reserved/shortage; restore verifies current reservation invariants without requiring stale backup reservations after lots have expired.

Events invalidate connected clients. Foreground/online snapshots also refresh every 15 seconds as transport fallback; background refresh is disabled. Stale writes still reject under expectedVersion and idempotent uncertain retries reuse original UUID.

Audit records command ID, entity ID, operation, timestamp and reason. Anonymous actor_id is null: the log does not invent an operator identity. Current public access policy is inherited and documented, not authentication.

## Payments and pickup dates revision

Apply `20261023150000_payments_pickup_calendar.sql` after the business expansion. Snapshot/export remain v2 and add `pickup_closures` (closed dates only), nullable `orders.transfer_name` and `financial_movements.transfer_name` (maximum 200 characters). Save-order paid status collects only the remaining balance atomically; unpaid cannot delete receipts or mark an already settled order unpaid. Omitting the status preserves earlier behavior. Paid state is derived from the signed financial ledger, not `payment_method`. Partial receipts remain supported. Transfer names can be recorded during unpaid delivery and reused at settlement. Rescheduling, closing, creation and payment all share the advisory lock, with idempotency checked before optimistic versions.

The app requires `pickup_closures` in the snapshot to detect an unmigrated server and uses a fresh persisted-query cache revision. Recovery accepts older v2 exports with absent closures and absent transfer names; absent fields default to an empty table/null. New exports preserve closures and transfer names, including financial reversals.
